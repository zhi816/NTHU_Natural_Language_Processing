CFEVER v3 訓練全流程

這份補充了最前面的「資料來源與 JSON / JSONL 檔案流向」，再接續完整的訓練與推論流程：notebook 由上往下跑一次，train、dev、test 三份資料一起走過同一條檢索流水線，但各自用途不同。

0. 資料從哪裡來：各個 JSONL / JSON 檔案說明

為什麼本地資料夾沒有看到 wiki_pages.jsonl？

本地的 nthu-nlp-ass3-fact/ 資料夾目前只有 train.jsonl（5.6 MB）、dev.jsonl（696 KB）、test.jsonl（771 KB）和 sample_submission.csv。wiki_pages.jsonl 檔案高達約 1 GB（收錄一百多萬頁維基百科），因為容量太大沒有一起放在這個本地資料夾裡；它是從 Kaggle 競賽頁面（nthu-nlp-2026-assignment-3-fact-verification）下載的完整資料集的一部分。在 Kaggle 執行時直接掛載 /kaggle/input/，在 Colab 執行時則是把整包競賽 .zip 放到 Google Drive 的 nlp-hw3/，第 1 節程式會自動把這 4 個 .jsonl 解壓縮出來讀取。

檔名來源 / 存放位置裡面有什麼欄位與資料
wiki_pages.jsonl輸入 Kaggle 競賽包（約 1 GB，百萬頁）每行一個維基頁面：id（頁名）、text（內文）、lines（句號\t句子，檢索時靠它保留原始句號）。
train.jsonl輸入 競賽包 / 本地 nthu-nlp-ass3-fact/24,012 筆訓練題：id、claim、label（S / R / NEI）、evidence（標準證據座標）、domain。
dev.jsonl輸入 競賽包 / 本地 nthu-nlp-ass3-fact/3,000 筆驗證題：欄位同 train.jsonl。只用來挑參數、選模型與評估分數，不參與梯度更新。
test.jsonl輸入 競賽包 / 本地 nthu-nlp-ass3-fact/測試題：只有 id 和 claim，沒有 label 與 evidence。
retrieval_cache.json產出 第 3 節存入 output_v3/存下檢索後的 5 句證據文字、dev_top_scores、test_top_scores 等。設 LOAD_RETRIEVAL_CACHE=True 可跳過檢索直接從第 4 節開始跑。
pred_*.json產出 第 4 節存入 output_v3/三個分類器各自存一份（pred_chinese-roberta-wwm-ext-large.json 等），記錄 dev_logits、test_logits 與輸入指紋，斷線重跑自動讀檔免重訓。
metrics.json產出 第 7 節存入 output_v3/記錄本次執行的 Recall、Accuracy、FEVER score 等指標，方便填寫報告與跨版本比較。

先抓三個重點

  1. 只有兩個地方在訓練。第 3 步微調 reranker（M2），第 6 步訓練三個分類器（M3～M5）。M1 bge-m3 全程不訓練，直接用現成權重。
  2. 訓練有先後順序。M2 要先訓練好，才能決定每題的 5 句證據；有了證據，才能組出分類器的訓練資料。所以 M3～M5 一定排在 M2 之後。
  3. 只有 train 會更新權重。dev 只用來「挑」：挑 bonus、決定 M2 要不要用微調版、選 epoch、選模型組合、NEI bias 和門檻。test 只拿 claim 來預測。
模型推論（不更新權重） 模型訓練（會更新權重） 不是模型的步驟 在 dev 上比較、挑選 資料 有訓練的步驟

三份資料各自的用途

資料會拿來更新權重嗎用在哪裡
train會第 3 步：取 8,000 題 S/R 微調 M2。第 6 步：全部拿來訓練 M3M4M5。
dev不會挑 bonus、決定 M2 要不要用微調版、每個分類器選最好的 epoch、選模型組合、挑 NEI bias 和門檻，以及報告裡的分數。
test不會只讀 id 和 claim，走一遍推論後輸出 submission.csv。

dev 被拿來挑了很多東西，所以 dev 上的分數會比真實表現稍微樂觀，notebook 報告第 4 題 (7) 也有提到這點。另外，三個分類器每訓練完一個就把 dev / test 的 logits 存成 pred_模型名.json，Colab 斷線重跑時會直接讀檔，不用從頭訓練。
