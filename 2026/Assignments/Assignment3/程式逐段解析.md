## 0. 先看一筆資料會怎麼流動

假設 claim 是「某城市位於甲國」，標準標籤是 `supports`，標準證據有兩組：

```python
evidence = [
    [[10, 20, '城市頁面', 3], [10, 21, '國家頁面', 5]],  # 兩句都需要
    [[11, 22, '歷史頁面', 8]],                          # 或找到這一句
]
```

第一組需要「城市頁面第 3 句」**以及**「國家頁面第 5 句」；第二組只需要「歷史頁面第 8 句」。如果程式找回第二組完整的那一句，證據評估就可以命中，不需要兩組都找到。

實際流程是：讀取 claim → 在候選頁面排序 → 取前 `DOCUMENT_TOP_K` 頁 → 只在這些頁面內排序句子 → 取前 `EVIDENCE_TOP_K` 句 → 把句子與 claim 輸入分類器 → 輸出標籤及 `[[頁名, 句號], ...]`。標準證據只用來建立訓練頁面候選庫、提供訓練標籤與計算 dev 分數；測試時沒有使用 test 的標準證據或標籤。

## 2. 文件檢索

### `gold_groups` 和候選頁面

`gold_groups(evidence)` 接收巢狀清單，回傳每組證據的 `(page_title, sentence_id)` 集合。題目中的標註格式有四欄，這裡使用索引 2 的頁名與索引 3 的句號。若一組為空或欄位無效，整組不算有效證據。

為何需要檢查空集合？Python 中 `set().issubset(任何集合)` 會是 `True`。如果直接把空證據組拿去評分，就可能把根本沒有標準證據的資料誤記成命中。

`wanted_pages` 是 set；對所有 `all_train_df` 的非 NEI 列，將有效標註中的頁名加入。set 會自動去重。接著逐行讀 `wiki_pages.jsonl`，只有 `page['id'] in wanted_pages` 才放入 `wiki_pages` 字典。它不會因為 dev 的標準答案而新增頁面。

注意 `TRAIN_SAMPLES = 3000` 只控制分類器的訓練 claim 數，頁面候選庫仍由 **全部** 公開訓練資料的標註建構。若 dev 的證據頁面不在這個庫中，調整排序也不可能找到它。

### `encode_texts`：值得手打的核心 1

檢索模型先以 `AutoModel` 載入，`.eval()` 關閉 dropout，`requires_grad_(False)` 凍結權重；印出參數量並檢查是否小於 1B。以下假設 batch 內有 `B` 段文字、補齊後長度 `L`、BERT 隱藏維度 `H = 768`：

```python
token_vectors = retrieval_model(**inputs).last_hidden_state  # [B, L, H]
mask = inputs['attention_mask'].unsqueeze(-1).float()        # [B, L, 1]
vector_sum = (token_vectors * mask).sum(dim=1)               # [B, H]
token_count = mask.sum(dim=1).clamp(min=1)                   # [B, 1]
text_vectors = F.normalize(vector_sum / token_count, p=2, dim=1)
```

- tokenizer 將文字轉成 `input_ids`、`attention_mask` 等 tensor。`padding=True` 讓同一 batch 的長度一致；`truncation=True` 把超過上限的內容截斷。
- BERT 針對每個 token 輸出一個 `H` 維向量。`unsqueeze(-1)` 讓 mask 的 `[B, L]` 變 `[B, L, 1]`，可以透過 broadcasting 與每個 token 向量相乘。
- mask 的 0 遮住 padding，1 保留有效 token。這裡特殊 token 只要 mask 是 1，也會參與平均；程式沒有另行排除 `[CLS]` / `[SEP]`。
- `sum(dim=1)` 沿 token 維度加總，再除以未遮罩 token 數，就是 mean pooling。`clamp(min=1)` 避免除以 0。
- `F.normalize(..., p=2, dim=1)` 把每一筆非零向量正規化為長度 1。兩個單位向量的內積等於 cosine similarity。
- `torch.no_grad()` 不建立梯度圖，`.cpu()` 把結果移回 CPU；各 batch 最後用 `torch.cat(..., dim=0)` 接起來。

### 建立 `document_embeddings`

`page_titles = sorted(wiki_pages)` 把字典的頁名依固定順序變清單。`document_texts` 的第 `i` 筆由同一頁的標題和前 6000 個字元組成；接著 tokenizer 還會按 `RETRIEVAL_MAX_LENGTH` 截斷，因此並非 BERT 一定讀到 6000 字。若共有 `P` 頁，`document_embeddings` 形狀是 `[P, 768]`，第 `i` 列對應 `page_titles[i]`。

### `retrieve_documents`：值得手打的核心 2

```python
similarities = vectors @ document_embeddings.T
indices = similarities.topk(k=count, dim=1).indices
pages = [page_titles[index] for index in indices]
```

如果這批有 `B` 個 claim、共有 `P` 頁，`vectors` 為 `[B, 768]`，轉置後的文件矩陣為 `[768, P]`，結果是 `[B, P]`。第 `i` 列、第 `j` 欄是第 `i` 個 claim 和第 `j` 頁的相似度。數值大代表向量方向較接近，不代表文字一定具有事實支持關係。

`topk(..., dim=1)` 對每列選最大的 `count` 個分數並取其索引，再用索引回到 `page_titles`。`min(top_k, len(page_titles))` 防止候選頁數不夠時要求太多。用 `query_batch_size=256` 分批算，避免一次建立所有 claim 乘所有頁面的巨大矩陣。train、dev、test 各自編碼、各自取得同順序的文件清單。

### 文件 Recall 與候選涵蓋率

`is_verifiable(row)` 只挑 `SUPPORTS` / `REFUTES`。`document_group_hit(groups, predicted_pages)` 對每一組取出所需頁名，判斷是否為預測頁面的子集合；任一組完整命中即可。

`document_recall = document_hits / document_count`；`document_count` 是可驗證題數，不是整個 dev 筆數。沒有有效證據組的可驗證題仍計入分母但算未命中，程式另印出數量。`document_coverage` 用整個候選頁面庫取代 top-k 預測來算同樣的命中條件，是這個固定候選庫對 dev 文件 Recall 的涵蓋上限，不是分類準確率。

## 3. 證據檢索

### 整理句子

`selected_pages` 是 train、dev、test 的文件檢索結果所涵蓋頁面的聯集；這是為了只對實際會用到的頁面編碼。它會使用 test claim 找出的頁面，但不讀 test 答案。對其中每頁的 `lines` 逐行處理：

```python
parts = line.split('\t')
sentence_id, text = int(parts[0]), parts[1].strip()
```

原始 `lines` 使用 `句號\t句子內容`，其後可能有其他以 tab 分隔的資料。忽略空行及沒有數字句號的行；保留原始 `sentence_id`，即使中間跳過空句也不重新編號。`sentence_info[i]` 存 `(頁名, 句號)`，`sentence_texts[i]` 存同一句的文字；`page_to_sentence_indices[頁名]` 存該頁所有句子的索引。

對 `sentence_texts` 執行同一個 `encode_texts` 得到 `[S, 768]`。不同於起始範例只使用訓練集標註句，這裡包含取回頁面的非空句子，所以候選可能變多、編碼時間也可能增加。完成後將檢索 BERT 移離 GPU 並刪除，減少後續分類器訓練佔用的 GPU 記憶體；CPU 上的向量仍保留供排序。

### `retrieve_evidence`：值得手打的核心 3

```python
candidate_indices = [index for title in pages
                     for index in page_to_sentence_indices.get(title, [])]
scores = sentence_embeddings[candidate_indices] @ claim_vector
for local_index in scores.topk(k=count).indices.tolist():
    index = candidate_indices[local_index]
```

`pages` 是**這個 claim** 的 top-k 文件；用字典只拿出這幾頁對應的句子，不必掃描整個句子庫。`scores` 一個元素對應一個候選句。`local_index` 是候選清單內的位置，不是整個 `sentence_info` 的索引，因此需要 `candidate_indices[local_index]` 才能查到正確頁名、句號與文字。

回傳兩個平行清單：`all_evidence` 放 `[[頁名, 句號], ...]`；`all_contexts` 把對應句子用空格連成文字，最多保留前 1000 個字元。分類 tokenizer 之後還有 192 token 的限制，所以太後面的句子可能被截掉。如果候選頁沒有非空句，該題回傳空證據與空 context。

### 證據 Recall

`evidence_group_hit` 把預測的 `[頁名, 句號]` 清單轉成 tuple set，因為 list 不能直接放進 set。`any(group.issubset(predicted) for group in groups)` 表示任一完整證據組存在即可。`evidence_recall` 使用同樣的可驗證題數當分母，評估的是「先取頁，再選句」的整體結果；頁面沒找對，後面的句子通常也找不到。

## 4. 分類：Dataset、模型、訓練、預測

### `ClaimDataset`

`labels = ['supports', 'refutes', 'NOT ENOUGH INFO']` 定義預測 ID 0、1、2 對應的輸出；`label_to_id` 將訓練集的標籤轉為整數。`train_labels` 先 `.str.upper()` 再對照，避免 supports 大小寫不同。

`ClaimDataset` 在初始化時把 claim、context 送入 tokenizer：

```python
tokenizer(list(claims), contexts, truncation=True,
          padding='max_length', max_length=MAX_LENGTH)
```

配對文字概念上是 `[CLS] claim [SEP] context [SEP]`；tokenizer 根據模型處理實際特殊 token。固定補到 `MAX_LENGTH`，讓 DataLoader 可以把每筆同欄位直接堆成 batch。

- `__len__` 告訴 DataLoader 資料筆數。
- `__getitem__(index)` 把該筆各欄轉成 `torch.long` tensor。訓練集有 `labels`；dev / test 只做預測，所以不附標籤給模型。
- 訓練 `DataLoader(..., shuffle=True)` 打亂順序；dev / test 用 `shuffle=False`，才能與原資料及檢索結果一一對應。

分類器訓練時使用實際檢索出的 `train_contexts`，而非保證正確的金標句。因此訓練輸入比較接近推論流程，但若檢索錯誤，訓練標籤與 context 也可能不匹配。

### 模型與 optimizer

`AutoModelForSequenceClassification.from_pretrained(..., num_labels=3)` 另載入一個 BERT 並建立三分類 head。分類 head 是新初始化的，載入時出現新權重提示通常是正常的；它需要後續訓練。這個分類器與前面凍結的檢索模型是**兩個模型實例**，不是在更新原來的檢索向量。程式檢查此模型的參數量也小於 1B。

`AdamW(model.parameters(), lr=LEARNING_RATE)` 接收可更新參數。程式把 `labels` 交給模型時，Transformers 的分類模型會回傳 cross-entropy loss。

### 訓練：值得手打的核心 4

```python
optimizer.zero_grad()                                      # 清除上一批留下的梯度
outputs = model(**batch)                                   # 前向運算，含 labels 時計算 loss
loss = outputs.loss
loss.backward()                                           # 計算每個參數對 loss 的梯度
torch.nn.utils.clip_grad_norm_(model.parameters(), 1.0)    # 限制梯度整體範數
optimizer.step()                                          # 根據梯度更新參數
```

外層 `for epoch in range(EPOCHS)` 代表資料巡覽的輪數；內層由 `train_loader` 取 batch。每個 tensor 先 `.to(device)`，`model.train()` 啟用訓練模式。`total_loss / step` 是目前 epoch 到該 step 的平均 batch loss；它不是 Accuracy。

訓練後 `model.save_pretrained(...)` 和 `tokenizer.save_pretrained(...)` 將分類器與 tokenizer 存到 `OUTPUT_DIR/finetuned_bert/`。在 Colab 這是 Drive 路徑；要等儲存完成再關閉頁面。

### `predict_labels` 與 Accuracy

`model.eval()` 切換推論模式，`torch.no_grad()` 不建梯度；`model(**batch).logits` 形狀為 `[batch, 3]`。`argmax(dim=1)` 取每列最高分的 ID，再以 `labels[label_id]` 轉回字串。這裡沒有設定信心閾值，NEI 是三分類器直接預測的一類。

Accuracy 的分子是預測標籤與 dev 標籤一致的題數，分母是全部 dev 題數（含 NEI）。它使用檢索到的 context，但評分時不檢查證據；因此 Accuracy 高不代表證據一定正確。

## 5. 三階段摘要與本地 strict score

`metrics` 同時保存訓練／驗證筆數、可驗證題數、兩個 top-k 和命中數、Recall、候選頁面涵蓋率、Accuracy、模型參數量、seed、`local_strict_score`。`json.dumps(..., ensure_ascii=False, indent=2)` 生成較容易閱讀的 JSON，輸出到 `metrics.json`；同一節也印出可複製到 Report 的數字。

本地 strict score 對 NEI 只要求標籤正確；對 SUPPORTS／REFUTES，要求標籤正確且前 5 句涵蓋任一完整標準證據組。它是這個 notebook 的本地估計，正式分數以競賽評分器與提交結果為準。如果把 `EVIDENCE_TOP_K` 調到超過 5，本地 strict 仍只看前 5 句。
